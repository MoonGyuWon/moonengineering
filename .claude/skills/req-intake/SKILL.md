# req-intake — 문제 읽기 · 질문 선정 · 스테이크홀더 · 요구사항 (0~3단계)

> **요구사항을 받아내는 스킬이다.** 설계(노드 · 상태)도, 코드도 만들지 않는다.
> 끝나면 `specs/REQUIREMENTS.md` 의 harness 블록이 `APPROVED` 이고 `python harness/validate.py` 7행이 OK 다.

> **시작할 때 `AGENTS.md` 를 읽는다** (역질문 · 그래프 규칙 · 종료 코드). 산출물(specs/ · trace/ …)은 지금 연 프로젝트 폴더에 만든다.

## 절대 규칙

```text
1 단계를 건너뛰지 않는다. 0 → 1 → 2 → 3, 단계마다 사람 확인을 받는다
2 질문은 질문 은행에서 고른다. 한 라운드 3~4개 · 질문 도구(없으면 채팅) · 첫 선택지는 권장안(+ 이유 한 줄)
3 사용자가 준 자료에 답이 있으면 묻지 않는다 — "이렇게 읽었다"로 확인만 받는다
4 기본값으로 채운 것은 반드시 가정표에 적는다. 말없이 채우지 않는다
5 수용 기준이 값으로 판정되지 않으면("잘 동작한다") REQ 를 확정하지 않는다 — 다시 묻는다
6 스테이크홀더끼리 충돌하면 고르지 않는다. 충돌을 이름 붙여 사람에게 고르게 한다
7 요구가 과하거나 방향이 틀렸다고 보이면 근거를 들어 말한다 (AGENTS.md 1절)
8 APPROVED 는 사람이 "승인"이라고 말한 뒤에만 쓴다
```

## 0단계 — 문제 읽기

1. 사용자가 준 문제 · 자료를 읽는다. 다 읽지 못했으면 그렇다고 말한다.
2. 분류한다.
   - **유형**: CLI 도구 · 웹 화면 · 데이터 처리 · 버그 수정 · 리팩터링 · 문서 · 자동화 …
   - **규모**:

     | 규모 | 판단 기준 | 이후 모드 |
     | --- | --- | --- |
     | S | 모듈 1개 · 1~3단계 | 체크리스트 한 장 (`templates/CHECKLIST.md`) · 필수 질문만 |
     | M | 모듈 여러 개 — 경계를 넘는 계약이 있다 | 계약 먼저 + 체크리스트 (모듈마다 단계) · 구조 질문 추가 |
     | L | 여러 모듈이 동시에 · 외부 부작용 · 병렬 에이전트 · 여러 스테이크홀더 | 개발 그래프 (계약 → 노드 웨이브 · HUMAN 승인 · 이벤트 추적) |

     규모는 **개발 과정의 무게**다. 완성품을 그래프로 만들지는 graph-plan 의 만드는 법 카드(`templates/BLUEPRINT.md`)가 따로 정한다.
3. 사람에게 확인받는다: "이 문제를 이렇게 이해했다 · 규모는 M 이다" — 질문 (규모 선택지 + 이해 요약).

## 1단계 — 질문 선정

1. `templates/QUESTION_BANK.md` 를 읽는다.
2. 등급으로 고른다: **A 필수**(항상) · **B 구조**(이 문제에 해당할 때) · **C 기본값**(묻지 않고 가정표로).
   규모별로 S 는 A 만, M 은 A + 해당 B, L 은 A + B 전부.
3. 질문 은행 맨 아래의 형식으로 **물을 것 / 가정표에 둘 것** 목록을 보여 주고 승인받는다.
   이 목록이 이후 라운드의 순서다. 사람이 빼거나 더한 것을 반영한다.
4. `specs/REQUIREMENTS.md` 를 `templates/REQUIREMENTS.md` 에서 복사해 만들고, 0절(문제 이해 · 고른 질문)을 채운다.

## 2단계 — 스테이크홀더 (Q2 묶음)

- 쓰는 사람 · 결정하는 사람 · 영향받는 쪽을 묻는다. 각자의 성공 기준을 받는다.
- 충돌 지점을 찾아 이름 붙인다 (예: "분석가는 빠른 결과, 운영은 원본 데이터 불변").
- REQUIREMENTS 1절 표와 harness 블록 `stakeholders` 를 채운다.
- 확인: "스테이크홀더를 이렇게 정리했다" — 승인받고 3단계로.

## 3단계 — 요구사항

순서: GOAL · 산출물(Q1) → 기능(Q3) → 품질 · 제약(Q5) → **수용 기준(Q4, REQ 마다)** → 하지 않는 것 → 불변(Q6) → 종료 · 이관(Q7) → (L) 설계 결정(Q8).

- REQ 하나에 수용 기준 하나 이상. "무엇을 재면 통과인가"를 명령 · 숫자 · 파일 · 사람 확인 중 하나로.
  사람만 확인할 수 있는 것은 `"verify": "human"` — 나중에 HUMAN 노드나 사람 확인 단계가 된다.
- 모호한 REQ 가 여럿이면 **모호도(score 1~5)** 를 스스로 매겨 높은 것부터 묻는다 (매긴 값은 질문 순서에만 쓴다).
- 답이 오면 바로 REQUIREMENTS 표와 harness 블록을 갱신한다. 아직 답이 없는 것은 `open_questions` 에 둔다.
- 라운드를 반복한다. **종료 조건**: `open_questions` 가 비고, 모든 REQ 에 값으로 판정되는 `acceptance` 가 있다.
- **라운드 상한 3회.** 3라운드 뒤에도 미결이 남으면 남은 질문을 보여 주고 묻는다 — "남은 것은 가정표로 두고 승인 / 한 라운드 더 / 범위를 줄임".

## 3-b단계 — 도구 선정 (B 등급 · M/L 기본 · S 는 외부 도구가 필요할 때만)

요구사항이 정해진 뒤, 계약을 쓰기 전에 **무엇으로 만들지**를 정한다 (`templates/QUESTION_BANK.md` Q9).

1. REQ 에서 **필요한 능력**을 뽑는다 (예: "PDF 에서 표 추출" · "웹 화면" · "저장소" · "테스트"). 능력마다 맡는 REQ 를 적는다.
2. 능력마다 후보 2~3개를 만든다. **"표준 라이브러리 / 직접 구현"은 가능하면 언제나 후보에 넣는다** (가벼움 우선).
   - 웹 검색을 쓸 수 있는 도구면 **검색해서 확인한다** — 최근 릴리스 · 라이선스 · 설치 방법 · 이 OS 지원.
   - 검색을 못 하면 알고 있는 정보로 쓰되 출처 칸에 **"알고 있는 정보 (확인 안 함)"** 이라고 적는다. 확인한 척하지 않는다.
   - 이 PC 에 이미 있는지는 직접 확인한다 (`--version` · import).
3. 비교 표를 보여 주고 묻는다 (첫 선택지 = 권장 + 이유 한 줄):

   ```text
   능력      후보            맞는 REQ   의존성 · 설치      라이선스   유지보수(최근 릴리스)   이 PC   출처
   PDF 표    pdfplumber      REQ-F2    pip 1개 + 의존 3   MIT       2026-xx                 없음    웹 확인 2026-10-31 <URL>
             표준 라이브러리   REQ-F2    없음              -         -                       있음    -  (표 추출은 직접 구현 — 정확도 낮음)
   ```
4. 고른 것을 REQUIREMENTS `tools` 에 적는다 (`status: decided` · `choice` · `candidates` · `reason` · `source`). 미정이 있으면 validate 7행이 SHORT 다.
5. 설치 · 계정 · 비용이 드는 도구는 고른 것만으로 설치하지 않는다 — 설치는 graph-plan W0 의 환경 확인에서 사람 승인 뒤에.

## 끝내기

1. 요구사항 전체를 요약해 보여 준다 (스테이크홀더 · REQ 표 · 하지 않는 것 · 가정표).
2. 묻는다: "승인 / 고칠 곳 있음". 승인이면 `status` 를 `APPROVED` 로.
3. 검사한다.

   ```bash
   python harness/validate.py --project <프로젝트>      # 7행 OK 여야 한다 (그래프가 아직 없으면 1행 SHORT 는 정상)
   ```
4. 넘긴다: `graph-plan` 이 만드는 법 카드를 쓰고, S · M 은 체크리스트 · L 은 개발 그래프를 만든다.

## 하지 않는 것

- 노드 · 상태 스키마 · 코드 작성 (graph-plan · graph-run 의 일)
- 질문 은행에 없는 질문을 쏟아붓기 — 꼭 필요한 새 질문은 이유를 말하고 묻는다
- 사람이 답하지 않은 칸을 그럴듯하게 채우기
